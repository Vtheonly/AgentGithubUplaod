# ADR-030: Financial rows carry a persisted academic-year attribution (nullable FK), with INV-14 as the documented fallback

- **Status:** Accepted (2026-09-29, 115th session — problems DATA-051/DATA-052/UI-318, task T-436 / the owner's Year-Tracking issue)
- **Context:** Every academic-year attribution in the finance feature was DATE-DERIVED (T-405's INV-14 windows on `due_date`; T-431's Sept-1 billing window for scoping): `installments`, `payments`, `ledger_entries` and `payment_allocations` carry no academic-year column. The owner's Year-Tracking mandate requires distinguishing (a) the year a charge was created/belongs to, (b) the year a payment was made in, and (c) the year of the debt a payment settles — and requires that an old debt NEVER be re-attributed to a newer year because the student re-enrolled or paid later. A per-row échéance edit (the Tranches tab's "Modifier l'échéance") silently re-attributes a charge across years on every date-derived surface; a cross-year settlement ("paid in 2026-2027 toward 2025-2026 debt") is structurally unattributable; the only DB-side carrier (`installments.service_enrollment_id → service_enrollments.academic_year_id`) is unused by the desktop and NULL for every bulk-imported row. Separately, `upsert_installment_from_import` (0037) already ACCEPTS a `p_academic_year` parameter it silently drops.
- **Decision:**
  1. **Add nullable `academic_year_id uuid → academic_years(id)` to `installments`, `payments`, and `payment_allocations`** (migration 0127). Semantics: on `installments` = the charge-belonging year; on `payments` = the payment-made year; on `payment_allocations` = the settlement-target year (denormalized from the allocated installment at allocation time, so the settlement history is immutable against later re-attribution). `ledger_entries` stays attribution-free — payment behavior already replays from it by date, and duplicating a fourth column there would serve no read path that `payments`/`payment_allocations` do not already cover.
  2. **Backfill with the same INV-14 rule the engines already use** (installments by the `due_date` window; payments by the `collected_at` window; allocations by joining the allocated installment) — the convention becomes a persisted fact for every existing row; the migration is one transaction with the schema_migrations registration (T-091/MIG-TOKENS pattern).
  3. **Attribution precedence everywhere: persisted column → INV-14 date fallback** (financial-rules §17.1/INV-18a). One precedence function per platform; NULL columns (edge rows, un-stamped writes) keep working through the documented fallback. This is NOT a second attribution system — INV-14 moves from "the rule" to "the fallback of the rule".
  4. **The canonical write paths stamp the columns:** `collect_and_allocate_payment` is recreated (0127) writing the payment's year (resolved from the collection date) and each allocation's target year (from the allocated installment's persisted/attributed year); `upsert_installment_from_import` is recreated wiring its previously-dropped `p_academic_year` (resolve code/label → `academic_years` row → INV-14 fallback on `due_date`).
  5. **`due_date` edits never touch the year column** (`updateDueDate` updates the date only) — the freeze that fixes DATA-051's silent re-attribution drift.
  6. **Historical amounts are untouched (INV-1/INV-19a):** the column carries attribution, never amounts; `amount_due` remains the price actually applied at creation; the per-year pricing configuration is REFERENCED through `pricing_configs.academic_year_id` (ADR-025), never duplicated.
  7. **The read side is the canonical TS engine** (`year-history.ts` — AGENTS.md §8: the desktop TS engine is the reference for read-side computations) over the canonical collections the repositories already load; the 0126-recreated `compute_debt_aging_rows` re-bases its attribution on the same precedence so the debt-aging SQL mirror stays parity-pinned with the TS engine.
- **Consequences:**
  - Cross-year questions become first-class: "who owed what at the end of 2025-2026", "which 2025-2026 debt was settled by 2026-2027 payments and exactly when" are queries/allocation reads, not reconstructions.
  - The desktop TS models gain optional `academicYearId` fields (additive — every existing consumer compiles unchanged; the mock store mirrors the fields for parity).
  - A future `academic_years` row deletion is NOT supported (rows are archived, `is_archived`, never hard-deleted — the FK freezes history); a year row that disappears would leave the column dangling, which the precedence's id-resolution failure handles by falling back to INV-14.
  - The Android/website contracts are additive-optional (the columns flow through the `*`-select RPCs and typed row shapes; consumers that ignore them keep working) — the cross-platform port of the year-history surface is future work, registered in T-436's Left.
  - Migration numbering: 0127 is the next free number (0122 remains reserved for IMPORT-118's flush RPC).
