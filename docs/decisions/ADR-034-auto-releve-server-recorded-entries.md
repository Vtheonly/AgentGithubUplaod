# ADR-034: The Auto-Relevé Becomes a Server-Recorded Exempted Entry Kind (UNKNOWN-030 settled: option (a))

- **Status:** ACCEPTED (2026-10-04, 140th session — T-482 / UNKNOWN-030; the owner's session mandate — "read the full audit and fix what was listed in this audit", delivered with the full infrastructure token set — delegated the ruling to the session, the ADR-033 precedent)
- **Context:** UNKNOWN-030 (registered by T-477's Personnel-page audit, 2026-10-04): the domain's Teacher Activity Ledger wants an **AUTOMATED operational activity ledger per teacher** (vault §09.06 — auto entries when a teacher enters grades / pushes homework / submits roll call), but the canonical `releve_entries` contract (0009) makes those impossible: the 0019 RLS allows INSERT only for the staff quartet (super_admin/financial_officer/support_staff/manager), and the `prevent_self_releve_entry` trigger raises whenever `recorded_by == personnel.user_id` — a teacher's own auto-entry fires the trigger by construction. The T-481 port therefore left the desktop's Supabase-mode teacher ledger admin-recorded-only (the honest state) and registered the owner question. The 139th session's closeout listed it as the audit's #1 remaining item; the owner's 140th-session mandate resolves it.

## Decision

**The auto-Relevé is wanted, and it is server-recorded.** Migration 0141 introduces:

1. **An exempted auto entry kind** — `releve_entries.entry_source` (`'manual' | 'auto'`, default `'manual'`) + `releve_entries.auto_kind` (`'grade_entry' | 'homework_push' | 'roll_call'`, nullable, CHECK-coupled: a manual row never carries an auto_kind, an auto row always does). Every pre-0141 row is `manual` by the default — no data change.
2. **The §09.05 self-entry ban re-scoped to manual rows** — `prevent_self_releve_entry` (replaced append-only) returns early for `entry_source = 'auto'`. The manual path is UNCHANGED: a teacher still cannot record their own manual entry, and the RLS insert policy (staff quartet only) still applies to manual rows.
3. **A canonical `record_auto_releve_entry(p_kind, p_class_id, p_class_subject_id, p_note)` RPC, SECURITY DEFINER** — the ONLY sanctioned writer of auto rows. It resolves the CALLER's own personnel row (`user_id = auth.uid()`, tenant-scoped, not deleted), maps the kind to the activity vocabulary the mock already uses (`grade_entry → correction`, `homework_push → task`, `roll_call → supervision` — the 0140-widened wire code), and inserts with `recorded_by = auth.uid()`, `clock_in_at = now()`. A caller with no personnel row (an admin entering grades) returns NULL — §09.06 is a per-TEACHER ledger; there is nothing to auto-record.
4. **Desktop wiring as a fail-safe side effect** — the three Supabase classroom write paths (`enterGrade`/`enterGradesBatch`, `recordRollCall`, homework `push`) invoke the RPC after their canonical write succeeds. A releve failure NEVER breaks the primary write (the T-314 event-bridge pattern); the failure is console-warned, not swallowed silently — the grades ARE the user's action, the ledger row is the documented side effect.

## Why the RPC and not the alternatives (the ruling's reasoning)

- **Not a role-widened RLS for teacher inserts:** letting teachers INSERT `entry_source='auto'` rows directly would let any teacher fabricate arbitrary manual-shaped ledger rows too (the RLS cannot see the payload's future mutations), and it re-opens the §09.05 hole the 0009 trigger exists to close. The RPC path writes exactly one kind-checked shape.
- **Not server-side triggers on `assessments`/`homework`/`attendance_records` (yet):** the strongest possible design (no client involvement at all), but it degrades the ledger's semantics TODAY: a row-level trigger would emit one entry per assessment ROW (a 30-student batch = 30 ledger rows) where the domain's event is the BATCH; the roll-call path is per-student rows with no single submission boundary; and the note vocabulary ("Saisie groupée — N note(s)") is the client's batch context. The RPC keeps the event granularity the mock defined. A trigger-based hardening is REGISTERED as the future direction (see Consequences) — this ADR deliberately ships the contract that all three clients can call identically.
- **The residual risk, accepted by the ruling:** a teacher CAN call the RPC directly and fabricate auto rows (nothing server-side proves a classroom operation preceded it). Accepted because: (a) auto rows are kind-tagged and append-only — no update/delete exists (no update/delete RLS policies); (b) the ledger is an operational activity metric, not a payroll input (the payroll surfaces read `personnel.weeklyHours*` + `salary_*`, not releve rows); (c) every auto row carries `recorded_by` — the fabricator is identifiable in forensics; (d) cross-checking auto rows against the classroom tables is possible in any audit. This is the SAME trust posture as the mock's client-side auto-append (§09.06's original implementation), now with server-side kind/tenant/actor validation instead of none.

## Consequences

- Migration 0141 is append-only (the 0009 file untouched), applied live with the T-091/MIG-TOKENS atomic registration pattern; `verify_t-482.sql` proves the columns, the coupling CHECK, the scoped trigger, the RPC's catalog shape, and — inside BEGIN…ROLLBACK — the runtime behavior: a manual self-entry still RAISES, an auto-shaped self entry PASSES the trigger, the RPC exists with SECURITY DEFINER + the authenticated grant.
- The desktop's `SupabaseReleveRepository.mapRow` surfaces `autoKind` — the Relevé tab's existing "auto" badge (releve-tab.tsx) lights up for RPC-written rows with zero UI change.
- The mock's `auto-releve.ts` helpers stay for MOCK MODE ONLY (documented in their header) — the two implementations now write the same CONTRACT (kind → activity vocabulary identical), not the same storage.
- **Future hardening (registered, not blocking):** move the auto-recording into server-side triggers on the classroom tables (per the 0078 notification-fan-out precedent) once a batch/submission boundary exists server-side; the RPC stays as the compat path.
- The Android is unaffected today (its releve surface reads the Room cache; it does not pull `releve_entries` — verified in the 140th-session census), and the new columns are additive/nullable-defaulted, so a future Android pull needs no migration.
