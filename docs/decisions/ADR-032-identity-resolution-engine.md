# ADR-032: The ER-PMAE architecture — a pure-TS desktop identity engine behind the T-414 EntityMatcher seam, additive SQL persistence, canonical-RPC-only writes, per-desktop experimental gating

- **Status:** Accepted (2026-09-29, 117th session — problems IDENT-100/101/102, task T-438 / GitHub issues #15 + #16)
- **Context:** Issues #15/#16 mandate a complete User Aggregation / Identity Resolution capability (ingestion/normalization, blocking, deterministic + fuzzy matching, confidence bands, false-merge guardrails, clustering, canonical aggregation, provenance, reversible merge/unmerge, idempotency, HITL review, auditing, tests) that is EXPERIMENTAL, disabled by default, activated only via Settings → Experimental, merges nothing without explicit confirmation, and neither bypasses nor parallels the existing backup/sync/restore/financial systems. T-414 (ADR-026) already shipped the exact integration point: the `EntityMatcher` interface + `NoOpEntityMatcher` default, deliberately unwired. The issues' attached article prescribes another program's stack (REST endpoints, Python, NetworkX, a six-table DDL with varchar ids) — issue #15 itself states it is "NOT a prescriptive implementation to copy" and mandates adapting the goals to THIS application's architecture.
- **Decision:**
  1. **A pure-TS domain engine at `src/domain/identity/`** (normalize → block → compare → veto → score → cluster → synthesize), mirroring the established `domain/calc/*` reference-engine pattern: framework-free, React-free, Supabase-free, fully unit-testable, and the single implementation of every ER rule (identity-rules.md is the rules source of truth). No external matching/graph library — the Levenshtein, phonetic-key, and bridge-detection algorithms are implemented in-repo (the no-new-dependency discipline; the same reasoning as the in-repo timetable solver).
  2. **The ONE integration point is the T-414 `EntityMatcher` seam.** The import storage adapter's parent resolution consults the ER matcher when (and only when) the experimental flag is ON; a confirmed match binds the incoming row to the EXISTING canonical entity through the adapter's normal upsert path (the same path the legacy phone-match idempotency uses). Flag OFF ⇒ the `NoOpEntityMatcher` path ⇒ the legacy `BatchParentIndex` exact-match resolution, byte-identical to pre-T-438. No second write path is created anywhere: financial/academic writes happen exactly where they already do.
  3. **The canonical entity stays the person record.** ER-PMAE introduces NO new "canonical profile" table for persons — the surviving entity of any aggregation is an existing `parents`/`students` row (the ADR-031 principle: one person identity per canonical table). The engine's persistent artifacts are LINKAGE + PROVENANCE only: `er_source_observations` (the immutable analyzed source rows + payload hash), `er_match_proposals` (the scored proposals + evidence + decision state), `er_identity_edges` (active/negative/severed edges with confidence + evidence snapshot), `er_aggregation_events` (the append-only audit trail of merges/unmerges/review decisions, carrying the COMPLETE prior mapping for restorability). One additive migration (0130), tenant-scoped, RLS-guarded, staff-gated, self-registered (the T-091 pattern). The issue-#16 six-table DDL collapses into these four because canonical profiles already exist (its `canonical_profiles`/`profile_source_mapping` roles are fulfilled by `parents`/`students` + the edges).
  4. **Merge/unmerge is ONE transactional server RPC in Supabase mode** (`fn_er_merge_parents`), mirroring the PERF-501/502 composite pattern: re-point `students.parent_id`, `payments.parent_id`, `installments.parent_id`, `ledger_entries.parent_id` from the merged-away parent to the survivor + soft-delete the merged-away parent (the T-384 convention) + write the `er_aggregation_events` row with the complete prior mapping + one audit entry. Unmerge (`fn_er_unmerge_parents`) replays the recorded mapping in reverse and restores the soft-deleted parent. The mock implementation mirrors the same contract on the store. Client-side orchestration NEVER issues the re-pointing updates directly.
  5. **The experimental gate is per-desktop-local** (localStorage, the local-config convention): `el-imtiyaz:experimental:<key>`. An experimental opt-in must never ride the server `feature_flags` (which every operator shares); it must be a deliberate, local, reversible choice. Settings gains an « Expérimental » tab listing experimental capabilities (each OFF by default) with the ER-PMAE toggle as its first entry.
  6. **Backup/sync/restore integration, not duplication.** The mock-store gains the ER collections and `replaceOperationalState` swaps them with the operational set (a backup taken post-aggregation restores the full aggregation state; one taken pre-aggregation restores zero-residue); `snapshotState` gains the ER sections. The ER tables in Supabase mode persist through the normal repository read/write path (no separate sync queue kind; the sync queue's five staged kinds are untouched).
  7. **The review surfaces are additive UI**: the import modal gains an analysis/confirmation step between preview and commit (flag ON only), and Settings → Expérimental hosts the duplicate-candidates review queue + the merge history with unmerge actions. No existing surface changes behavior when the flag is OFF.
- **Consequences:**
  - The feature is complete, merged, and permanently dormant until a local opt-in — satisfying issue #15's "fully implemented… disabled/inactive and classified as Experimental".
  - The importer's identity resolution gains exactly one new dependency (the optional matcher), preserving the T-414 "engine stays generic" contract; a future format/matcher change plugs into the same seam.
  - Migration numbering: 0130 (next free; 0122 reserved; 0118 the documented gap).
  - The ER suite joins the unified Vitest Layer (ADR-029) under `src/tests/`; the baseline manifest must be updated only via the registered-change convention if the suite's totals move.
  - Risks accepted: the matcher's recall on very noisy data is bounded by the blocking passes (documented in identity-rules §3); merges on live data remain operator-driven (the review queue never auto-executes — INV-50).
