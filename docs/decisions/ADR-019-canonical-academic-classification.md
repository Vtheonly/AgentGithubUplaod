# ADR-019: Canonical academic classification — Niveau → Filière → Spécialité → Classe/Section

- **Status:** Accepted (2026-09-22, 85th session — task T-401, problem ACAD-501)
- **Context:** The system had **zero** filière/spécialité support before migration 0107. The only filière-adjacent field in the whole schema was `subject_configurations.direction text DEFAULT 'general'` (0094, ADR-018's documented residual: "until classes carry a real filière field"). The classification model required by the school — the Algerian secondary structure where 1AS is organized in troncs communs, 2AS/3AS in six national filières, and Technique Mathématique subdivides into génie spécialités — could not be represented at all: not on the student, not on the class, not in history, and therefore not in class formation, promotion, statistics, imports/exports, or any filter. T-401's mandate: treat **Niveau → Filière → Spécialité → Classe/Section** as ONE canonical model integrated end-to-end, with the catalog of valid values in the database — never a page-local enum.
- **Decision:**
  1. **The catalog is DATA, not code.** A new tenant-scoped `filieres` table (migration 0107 §1) holds filières AND their spécialités in one table — a spécialité is a row with `parent_code` set. Applicability is an explicit `applicable_grades text[]` list on the canonical 14-code ladder (never a range, so no ladder-ordering logic is ever needed). Seeded for every tenant that owns `academic_levels`: `general` (whole ladder) + 3 troncs communs (1AS) + the six national filières (2AS/3AS) + the 4 génie spécialités (children of `technique_mathematique`). The school extends it as data; the Gestion & Économie spécialités are deliberately NOT seeded (the school's actual practice is unconfirmed — recorded in `docs/recovery/unknowns.md`).
  2. **Three nullable classification columns, one semantics.** `classes`, `students` and `student_academic_histories` each gain `filiere_code`/`specialite_code` (0107 §2). **NULL means "untagged"** — the pre-0107 state of every existing row, which makes the change backward-compatible by construction. The literal string `'general'` is normalized to NULL at every write boundary (the import RPC, the desktop `normalizeTrackCode`, the finalize RPC's draft handler).
  3. **A filière and a classe are different concepts** (the academic-rules §9 rule): the class/section is the concrete student group; the filière is its academic stream context. A class's `filiere_code` is the stream the section teaches; a student's `filiere_code` is the stream they are enrolled in.
  4. **ONE compatibility predicate, mirrored three times under the lockstep rule.** The SQL `fn_track_compatible` (0107 §3) is the authoritative guard: an untagged class always passes (pre-0107 behavior); an untagged student can enter any tagged class (the assignment tags them); the same filière passes; a **differing filière that applies at the target grade is a CONFLICT**; a differing filière that does NOT apply (a 1AS tronc commun entering a 2AS filière) is **re-streaming** — the whole point of year-end class formation. A class tagged with a spécialité requires an equal student spécialité. The desktop mirrors it in `src/domain/model/filiere.ts` (`trackCompatible`), pinned by `src/tests/domain/academics/filiere.test.ts`; the website carries only the display labels (no business logic — read-only portal).
  5. **Class formation is the classification transition point.** `fn_finalize_class_placements` (0107 §4) validates drafted sections' codes against the catalog, runs the compatibility check per assignment (22023 on conflict, whole-batch rollback like the grade check), and **stamps the student's classification from a tagged class** — the legitimate way classification changes between academic years. Promotion deliberately does NOT change classification (the stream continues; the next year's formation may re-stream it).
  6. **Imports never erase classification.** `upsert_student_from_import` (0107 §5) gains `p_filiere_code`/`p_specialite_code` with COALESCE-preserve semantics: an omitted parameter keeps the stored value (the Android sync and the Excel import corpus — which has no filière column — can never destroy classification). `'general'` is treated as "not provided" on update, NULL-storage on insert.
  7. **History preserves the academic-year context of classification.** `execute_batch_promotion` (0107 §6) stamps each archived history row with the student's filière/spécialité in force during the completed year — read from the student row server-side, never trusted from the payload.
- **Consequences:**
  - Every pre-0107 client payload keeps working (all new RPC keys/params are optional); old clients simply operate in the untagged world.
  - The desktop domain carries the catalog mirror (`src/domain/model/filiere.ts`) under the same convention as `GRADE_LEVELS` vs `academic_levels` — the DB remains the source of truth the school can extend; the mirror feeds UI options, client-side validation and mock mode.
  - Deliberate omissions (recorded residuals): **no FK** from classes/students to `filieres` (the catalog is per-tenant seeded; future tenants are created without it — write paths validate codes instead), and **no trigger** on `students.class_id` enforcing compatibility (the Android offline sync pushes partial student rows and must never be rejected by a classification it does not know about). Compatibility is enforced at class formation (server + client) and in the desktop edit-form validation.
  - ADR-018's `direction` residual is now superseded in intent: a real classification model exists; wiring `subject_configurations.direction` to the class's filière (per-direction subject configurations) remains future work, registered in the task registry.
