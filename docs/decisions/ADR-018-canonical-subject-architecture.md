# ADR-018: Canonical subject architecture — identity separated from context configuration

- **Status:** Accepted (2026-09-14, 62nd session — problem MATIERE-500, tasks T-343…T-349)
- **Context:** The owner's commit 158d806 ("idk mattier is wrong") is the pain signal behind a structural defect family that the audits had each partially catalogued (ACAD-102, ACAD-104, REG-006's subject-surface fallout) but never root-caused as ONE problem: the "matière" concept is modeled differently in every layer, with the subject's IDENTITY and its per-context CONFIGURATION fused into a single row.
  - **Live evidence (census 2026-09-14, scripts/live_subject_census.sh):** the production `subjects` directory holds 12 rows, each frozen to ONE cycle with ONE coefficient ("Arabe" exists only as a *primaire* subject with coefficient 3 — a 4AM/CEM teacher cannot represent their Arabe course at its CEM coefficient; "Anglais" exists only for *cem*). `class_subjects` holds 3 rows (the assignment flow only started persisting 2026-09-12, T-313/ACAD-104); `assessments` holds 4 wide rows; the 0004 normalized `grades` path has 0 rows (dead in production).
  - The subject COEFFICIENT is stored in three places (`subjects.default_coefficient`, `class_subjects.coefficient`, `assessments.coefficient` snapshot) and resolved through 14 scattered per-surface fallback chains (`a.coefficient || subject?.coefficient || 1`) across the desktop features and the website — no canonical resolution rule, different fallback orders on different screens.
  - المراقبة المستمرة / le contrôle continu — the continuous-assessment mark that Algerian term averages are built from — has NO first-class representation: the wide assessment row carries exactly three fixed slots (devoir1, devoir2, examen) with weights hardcoded (1, 1, 2) in the SQL trigger `compute_assessments_subject_average` (0041) and the desktop `computeSubjectAverage`; the Android alone carries per-component coefficients (`coefficientDevoir1/2/Examen`) on its Subject model — a concept that exists on NO other platform.
  - There is no direction (filière / شعبة) dimension, no exam-session (séance de composition) entity, and no per-context passing grade — `subjects.passing_grade` is global per subject.
- **Decision:**
  1. **The canonical subject is an IDENTITY, not a configuration.** `subjects` rows answer "what is this matière" (code `MATH`, `name_fr`/`name_ar`/`name_en`, domain scolarite/club/therapy/auxiliary). The legacy context columns (`cycle`, `default_coefficient`, `passing_grade`, `is_extracurricular`) remain for backward compatibility but are NO LONGER authoritative once a configuration row exists (migration 0094 seeds one for every subject × level × year actually referenced by production classes, preserving the live values bit-for-bit).
  2. **A NEW `subject_configurations` table carries the CONTEXT**: one row per (tenant, subject, academic year, academic level, direction) with `coefficient`, `subject_code` (per-bulletin identifier, falls back to `subjects.code`), `passing_grade`, `is_extracurricular` (whether it counts toward the official GPA in that context), and `grading_recipe` (JSONB component weights: `devoir1`, `devoir2`, `examen`, `cc` — the contrôle-continu mark — each ≥ 0; a 0-weight component does not participate). One coefficient per context — never per ad-hoc UI fallback.
  3. **Coefficients never retroactively rewrite history.** Every assessment row SNAPSHOTS the resolution at entry (the existing `coefficient` + `coefficient_devoir1/2/examen` columns, joined by the NEW `coefficient_cc`); the GPA engines consume ONLY the snapshots. Editing a configuration affects FUTURE entries; a new academic year seeds NEW configuration rows (the previous year's rows are immutable evidence of what was in force).
  4. **المراقبة المستمرة (contrôle continu) is a first-class component.** The canonical subject-average rule generalizes to `subject_average = Σ(mark_k × weight_k) / Σ(weight_k)` over the recipe components, requiring ALL positive-weight components to be present (missing → not computable — the T-336 honesty rule). The seeded default recipe `{devoir1:1, devoir2:1, examen:2, cc:0}` is bit-identical to the current `(D1+D2+2×Ex)/4` engine on every platform; enabling `cc` for a context is an admin decision per subject-year-level, exactly like any coefficient change.
  5. **ONE canonical resolver per platform.** `resolveSubjectConfiguration` (desktop `src/domain/calc/academics/subject-config.ts`; verbatim website port in `src/lib/canonical/`; Kotlin mirror in `core/SubjectConfig.kt`) resolves (subject, level, year[, direction]) → configuration with the documented fallback chain (assessment snapshot → configuration row → legacy subject columns → 1). The 14 scattered `||`/`??` chains are replaced by calls to this resolver.
  6. **Exam sessions (séances de composition) get a first-class table** (`exam_sessions`: class, subject, kind from the recipe, scheduled date, room, max score) so the composition calendar is data, not hardcoded labels.
  7. **GPA semantics are unchanged at the formula level** (coefficient-weighted mean of subject averages, extracurricular excluded — `computeOverallGpa` / `fn_calculate_student_term_gpa`); what changes is that every INPUT (coefficient, weights, exclusion flag, passing grade) now flows from the context configuration through the snapshot discipline.
- **Consequences:**
  - A subject exists ONCE in the directory and is CONFIGURED per level/year/direction — "Mathematics in 5AP 2026-2027, coefficient 4, recipe {1,1,2,0}" and "Mathematics in 1AM 2027-2028, coefficient 5, recipe {cc:1, examen:2}" are rows of the same identity, and neither retroactively touches the other's historical results.
  - All three platforms resolve coefficients/weights through ONE function each, pinned equivalent by the cross-platform corpus (a `subject_configuration` category) instead of 14 divergent fallback chains.
  - The 0004 normalized `grades` path stays formally dead (0 production rows); the wide-row `assessments` shape is the working truth (source-of-truth registry already says so); no client may revive the normalized path.
  - Migration 0094 is ADDITIVE and idempotent (never edit applied migrations — §15.9); the live application follows the T-091/MIG-TOKENS atomic pattern (file + registration in one call).
  - Residual (owner-gated): the direction dimension defaults to `'general'` until classes carry a real filière field; per-direction configuration rows are structurally ready but no UI lists directions yet.
