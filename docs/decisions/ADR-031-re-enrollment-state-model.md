# ADR-031: The re-enrollment state model — one student identity, per-year enrollment records, candidates from finalized pedagogy, freeze-guaranteed decisions, target-year billing through the register_family_batch wire contract

- **Status:** Accepted (2026-09-29, 116th session — problems ACAD-512/BUSINESS-109/STUDENT-501/STUDENT-502/UI-319, task T-437 / GitHub issue #18)
- **Context:** The system is single-year in shape: the year-end transition exists only as the PROMOTION flow (the pedagogical result — `execute_batch_promotion` writes `student_academic_histories` and advances `students.grade_level_code`), and the only interactive billing writer is `register_family_batch` (new-family shaped). A student finishing one academic year and continuing into the next can therefore only be handled as a from-scratch new-family registration (duplicate-student risk — the exact failure issue #18 forbids) or with no year-2 enrollment/billing at all. Additionally the wizard's `presetParent` add-child leg shows a billing devis it never persists, there is no student-first creation entry point, and the pre-admission origin (previous school) is captured nowhere. T-436 already persisted the per-year financial attribution (`installments.academic_year_id` etc.) and the per-year history engine — the missing piece is the WORKFLOW that creates the next year's enrollment + billing on the SAME student.
- **Decision:**
  1. **A `re_enrollments` table (migration 0128) carries the year-transition state** — one row per `(tenant, student_id, target_academic_year_id)` (unique): the source-year finalized snapshot (source grade/class, `final_decision`, `final_average` copied from the history row at generation time for display stability), the `expected_grade_level_code` (INV-22c derivation), the `status` (`waiting | started | re_enrolled | not_continuing`), the decision provenance, and `frozen_at`. This is a NEW concept (there is no enrollment-per-year table in the CRM domain — `students` carries the current placement, `student_academic_histories` the archived years), so a new table is the minimal non-duplicative representation; it REFERENCES the canonical tables and never copies identity or financial data.
  2. **Candidates are GENERATED (materialized), not derived live.** `fn_generate_re_enrollment_candidates` inserts `waiting` rows for the eligible active roster of the source year, enriched from the finalized histories, ON CONFLICT DO NOTHING (idempotent — existing decisions survive regeneration; INV-21b). The review list (`fn_get_re_enrollment_candidates`) reads the table joined to the live student/parent/class data. Materialization (vs. pure derivation) is chosen because the red badge must count the PERSISTED waiting set, decisions must survive roster changes, and the freeze must have something to freeze.
  3. **The pass/fail facts come ONLY from `student_academic_histories`** (INV-22a — the promotion flow is the one writer; the re-enrollment never recomputes results). History-less candidates (the imported corpus pre-finalization) surface the honest « non finalisé » state (INV-22b).
  4. **`fn_re_enroll_student` is the ONE composite** for the accepted re-enrollment: lock + freeze-guard the candidate row → update the student's target-year placement (`grade_level_code`, optional `class_id`, `payment_plan`, `transport_tier`) → insert the CLIENT-DERIVED billing legs (money stays client-side per §15.39b — the exact `register_family_batch` wire shapes, reusing the EXTRACTED shared wire builder; the server fills the real uuids and stamps `academic_year_id = target`) → flip the status to `re_enrolled` → ONE audit. One transaction; the student's identity, parent links, histories and previous-year financial rows are untouched (INV-21a/21c, INV-26a).
  5. **The freeze is list-wide and completion-gated** (INV-23b): `fn_freeze_re_enrollments` refuses while any `waiting` row remains for the target year, then stamps `frozen_at` on every row; the decision and re-enroll RPCs refuse frozen rows. This mirrors — and integrates with — the promotion cycle's completion semantics (ADR-028's human-in-the-loop year-end family) without sharing its table: the promotion cycle finalizes the SOURCE year's pedagogy; the re-enrollment freeze finalizes the TARGET year's roster decisions.
  6. **Student origin becomes first-class columns on `students`** (`origin_type` ∈ new_admission/transfer/continuation/other, `previous_school_name`, `previous_school_level`, `previous_academic_year`, `origin_notes`), threaded through `upsert_student_from_import` as trailing params (the 0112 pattern) and through `register_family_batch`'s jsonb column list (the §15.45a re-audit) — the SAME composite-param discipline the filière/specialité thread followed.
  7. **Direct student creation reuses the batch wizard**: the Élèves tab's « Ajouter un élève » opens the registration wizard in a direct mode whose first step is parent search-or-create (`ParentRepository.search` + the existing Step-1 form); an existing parent is bound by passing its ACTUAL parent code to `batchRegister` (new optional `existingParentCode` input) so the canonical `upsert_parent_from_import` identity match (tenant, parent_code) reuses the record — never a duplicate. The same mechanism repairs the `presetParent` leg's dropped billing (BUSINESS-109): the add-child leg now routes through the same one-transaction composite, so the shown devis is persisted.
  8. **RLS mirrors the promotion-cycle pattern** (0108): staff read, admin manage (`re_enrollments_staff_read` / `re_enrollments_admin_manage`), and every RPC resolves the tenant server-side and writes through `write_audit_log`.
- **Consequences:**
  - The Student = person / Enrollment = per-year registration distinction is enforced structurally: no code path in the flow creates a person; the per-year facts live in `re_enrollments` (decision) + `student_academic_histories` (results) + the year-stamped financial rows (billing).
  - The target-year billing is attributable with zero ambiguity (INV-25c) and immediately visible on the T-436 surfaces.
  - `batchRegister`'s contract gains one optional input (`existingParentCode`) — the mock and Supabase implementations stay parity-pinned; the composite-param drift trap (§15.45a) is respected by threading the origin columns through BOTH the RPC jsonb list and the trailing upsert params in the same migration.
  - The desktop domain gains `ReEnrollment*` models + a `ReEnrollmentRepository` contract (the PromotionCycleRepository pattern: the contract mirrors the RPCs 1:1, no client-side business logic) with Supabase + mock implementations (store-based parity).
  - The candidate generation ordering dependency (finalize-then-re-enroll) is a documented operational rule (academic-rules §10.2 INV-22d), not an enforced one — the honest « non finalisé » state covers the pre-finalization path.
  - Migration numbering: 0128 is the next free number (0122 remains reserved for IMPORT-118; 0118 is the documented gap).
