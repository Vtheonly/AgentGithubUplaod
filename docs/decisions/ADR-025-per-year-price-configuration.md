# ADR-025: Price configurations are per academic year with exactly one ACTIVE config per tenant

- **Status:** Accepted (2026-09-26, 99th session — problem PRICING-500, task T-414 / issue #14 Task 1)
- **Context:** The canonical pricing tables (migration 0006) already model one config per tenant per academic year (`pricing_configs unique (tenant_id, academic_year_id)` with child grids keyed by `pricing_config_id`), but the application layer collapsed this to a single anonymous config: `SupabasePricingRepository.activeConfigId()` picks the FIRST `is_active` row with no year predicate and auto-creates one bound to the current year when none exists; `readDbPricingConfig()` (also consumed by `batchRegister` billing) repeats the un-scoped read; the Settings → Tarification UI has no year dimension. Preparing a new academic year's prices could only be done by overwriting the previous year's rows — destroying the previous configuration's read-side and leaving nothing to switch to. The owner's issue #14 Task 1 mandates per-year independent configurations, one active, historical preservation, and an explicit switch.
- **Decision:**
  1. **One ACTIVE config per tenant, enforced at the DB level.** Migration 0117 adds the partial unique index `pricing_configs (tenant_id) where (is_active)` — the selection `.eq("is_active", true).limit(1)` becomes deterministic by construction, not by accident.
  2. **Activation is an explicit, atomic operation.** The `set_active_pricing_config(p_config_id uuid)` RPC (SECURITY DEFINER, tenant-verified, audited by the existing 0086 pricing mutation triggers) deactivates the tenant's other configs and activates the target in ONE transaction. There is no implicit activation side-channel.
  3. **New-year preparation is a create-then-activate flow.** `create_pricing_config_for_year(p_academic_year_id, p_label, p_clone_from_active)` creates the next year's config (cloning the active config's child grids when requested — the school's year-over-year changes are usually a delta), after which the owner edits prices and finally activates it. The `unique (tenant_id, academic_year_id)` constraint keeps one config per year.
  4. **`PricingRepository.observe()` returns the ACTIVE config — the single source of truth for new payments, invoices, parent charges, installments and financial calculations.** Year-scoped reads of other configs go through the new `readForYear` (read-only surface for comparison/audit). Pricing WRITE methods keep targeting the active config only; a historical (inactive) config is never mutated through the pricing editor.
  5. **Historical preservation is the existing INV-1 replay rule, unchanged.** Balances replay from stored `ledger_entries` / `service_enrollments` / `installments` rows; the catalog drives FUTURE quotes only (ADR-017 §4). Activating a new-year config therefore cannot silently recalculate historical financial records — there is no code path that recomputes stored financial rows from the active pricing config, and this task adds none.
  6. **The mock twin mirrors the same contract** (`listConfigs` / `activateConfig` / `createConfigForYear` / `readForYear` + active-scoped `observe`), so the desktop pricing UI works identically in mock and Supabase modes (ARCH parity).
- **Consequences:**
  - The Settings → Tarification tab gains a year-config bar: the active config's year is visible, other years' configs are viewable (read-only), new-year configs can be created (with clone), and activation is a confirm-guarded action.
  - `readDbPricingConfig()` stays ACTIVE-scoped (not year-parameterized): every financial calculation that consumes pricing (registration billing, wizard preview, import installments) keeps reading the active config — switching years changes future charges, never past records.
  - The 0089-realigned live config for 2026-2027 remains the active config after migration 0117 (the index validates, not mutates); creating the 2027-2028 config is an explicit owner action.
  - The corpus suite (`real-school-corpus.test.ts`) continues to pin the 2026/2027 workbook defaults — the per-year model changes WHERE prices live, not WHAT the 2026/2027 prices are.
