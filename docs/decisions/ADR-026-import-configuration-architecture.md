# ADR-026: Import configurations are versioned data documents resolved by a central registry; the engine stays format-agnostic

- **Status:** Accepted (2026-09-26, 99th session — problem IMPORT-111, task T-414 / issue #14 Task 2)
- **Context:** The generic import engine (T-105) was schema-driven, but its four schemas were hardcoded TS constants with HEADER-ONLY field addressing, and no repository managed them. The 2027-2026 workbook broke every assumption: its student-name column F has an EMPTY header cell (unmatchable), its three CREANCE SEPT columns SHARE one header (indistinguishable), its V2 column was relabeled V1, and its sheet NAME (`ETAT 20262027`) is IDENTICAL to the old format's — name-based detection cannot tell the formats apart. Supporting a new format had to mean editing engine-adjacent code, exactly what the mandate forbids ("never a per-format hardcoded importer").
- **Decision:**
  1. **A central `ImportConfigRegistry` (`src/infrastructure/excel/import-config/`) owns all import knowledge.** Every format is ONE `ImportConfigDocument` — versioned, JSON-serializable DATA describing sheets, column→canonical-field mappings, identity, validation options, per-column classification (identity/academic/contact/note/financial-charge/financial-payment/financial-informational/reference) and a documented `concept` per field. Registering, loading, identifying, selecting, validating, versioning, resolving and enabling/disabling all go through the registry.
  2. **The engine stays generic — it consumes compiled `ImportSchema`s.** `compileSheetConfig` translates documents into the engine's existing runtime schema type; `schemas/index.ts` is now a thin registry-backed shim (the legacy detection order ETAT → REF → BON → DEVIS preserved). Adding a format = registering a document; ZERO engine changes.
  3. **Column addressing is three-way:** `header` (classic), `headerAliases` (config-driven spellings), and `column` (POSITIONAL — letter A…ZZ, resolved via the parser's synthetic `__col_<LETTER>` row keys; takes precedence when set). Positional addressing is what makes the headerless column F and the shared-header CREANCE SEPT columns importable.
  4. **Format detection is name + header signature.** Tier 1 (sheet-name regex) shortlists; when several formats match the same NAME, the ACTUAL header row disambiguates — the config whose `requiredHeaders` are ALL present wins (most specific signature first, then `detectionPriority`). The engine's `processSheet` reads the real header row before detecting; explicit selection stays available (`ImportOptions.schemas` / `registry.selectConfig`).
  5. **The canonical import record is ONE contract shared by all formats.** The 2027-2026 config maps V1 → the canonical key `v2` (the adapters' "1st tuition installment" key) and PSY3–14/COURS SUP/LIVRES/CLUB/SORTIES → new keys on the SAME record shape. The `RepositoryStorageAdapter` (canonical entities + ledger + payments + installments + sync queue) is the ONLY storage path — imported financial data flows through the EXISTING financial ledger, never a second financial system (ADR-002).
  6. **Informational workbook columns are never ledgered** (TOTAL VERSEMENTS, TOTAL*CREANCE, CREANCE SEPT ×3, TT CREANCE): balances replay from stored ledger entries (INV-1); copying the workbook's own arrears math would create a parallel calculation system.
  7. **Extension points are INTERFACES ONLY (profile matching NOT implemented, by mandate):** `EntityMatcher` (+ `NoOpEntityMatcher` default — always "no match"), `ImportConfigStore` (a future DB-backed configuration store), `ImportValidationRule`, `ReconciliationHook`, `ImportSourceAdapter`. The core importer does not assume any of them exist.
  8. **The built-in configurations are code-resident data** (`import-config/configs/*.ts`, version-controlled); a DB-backed store can replace them later through the same `ImportConfigStore` seam without engine changes.
- **Consequences:**
  - The 2026-2027 format's four schemas are now DERIVED from its config document — one source of truth; the named exports (`ETAT_SCHEMA`, etc.) remain for compatibility (byte-equivalent field lists).
  - The parser emits `__col_<LETTER>` keys for every column; `lookupValue` resolves column-first, then header/aliases — header-keyed behavior is unchanged for columns with headers.
  - The 2027-2026 workbook's `statistiques ` sheet is EXCLUDED by its config (a #REF!-broken reporting surface — §15.53: analytics consumes the canonical engines).
  - Deep-comparison evidence and the full column mapping live in `docs/architecture/excel-format-comparison-2026-2027-vs-2027-2026.md` (written BEFORE the configuration was designed, per the mandate).
