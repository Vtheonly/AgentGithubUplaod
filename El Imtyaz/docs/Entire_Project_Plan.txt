# Four-Child Limit vs Unlimited N

> [!success] Surviving rule
> A Parent/Guardian profile can be linked to an **unlimited number ($N$) of dependent children**. The 4-child cap is removed.

## What changed

Early drafts capped batch registration at 4 children per parent. Later revisions explicitly removed the cap and replaced it with a dynamic, unlimited model.

## Why it changed

- Real families vary in size; a hard cap produced awkward edge cases.
- The batch workflow was already atomic, so scaling to $N$ added no integrity risk.
- Database schema can use a junction table or `parent_ids_json` to map $1 \rightarrow N$ without code limits.

## What this means in practice

- The registration form has an **"Add Another Child"** button with no upper bound.
- The atomic transaction (`BEGIN...COMMIT`) wraps parent plus all $N$ students.
- Parent profile drawers must render a list of $N$ linked children, not a fixed 4-slot grid.

## Common mistake

> [!caution] Do not
> Hard-code a 4-child array in UI components. Always render the children list dynamically from the database.

# Grok vs Groq

> [!success] Surviving rule
> The platform uses **Groq** (with a "Q") LPU API as its primary AI engine, plus OpenRouter as a multi-model gateway. References to xAI Grok are obsolete.

## What changed

Earlier drafts referenced "Grok" (xAI). The final revision corrects the name to **Groq** and emphasizes its LPU hardware and free-tier speed advantage.

## Why it changed

- Groq LPU inference is dramatically faster on the free tier than the xAI Grok API.
- The document explicitly notes "Groq with a Q" to disambiguate.
- The BYOK model still works for either provider, but defaults ship with Groq.

## What this means in practice

- Settings page labels should read **Groq**, not Grok.
- Default API key slots should target `https://api.groq.com/openai/v1`.
- OpenRouter remains the secondary gateway for model fallback.

## Common mistake

> [!caution] Do not
> Copy "Grok" branding from earlier drafts into UI strings or documentation. Always verify the spelling "Groq".

# Excel Engine Retention vs Deprecation

> [!success] Surviving rule
> The embedded Excel formula engine, Devis quote sheet reproduction, cell-matching logic, and column-AM text parsers are **100% deprecated and purged**. Excel survives only as a two-way data bridge: bulk student import and report export.

## What changed

Mid-tier drafts described a full Excel formula engine (`SUM`, `VLOOKUP`, `INDEX`, `MATCH`, `IF`, etc.), Devis quote block reproduction, and column-AM audit-comment parsing as live features. The final revision declares all of this purged.

## Why it changed

- Maintaining a parallel spreadsheet engine created duplicate logic with the relational database.
- Excel formulas are fragile, hard to audit, and impossible to secure at row level.
- All billing, quotes, and history can live natively in structured Supabase tables.

## What this means in practice

- The Desktop terminal can read `.xlsx` files **only** to bulk-import student rosters.
- The Desktop terminal can write `.xlsx` / `.csv` files **only** for external reporting.
- No formula evaluation, no cell-matching, no Devis sheet reproduction anywhere in the codebase.

## Common mistake

> [!caution] Do not
> Re-introduce `ExcelJS` formula parsing into runtime code paths. The library may remain imported, but only inside the import and export service modules.

# Scholarships vs Discretionary Adjustments

> [!success] Surviving rule
> The Scholarship system is **completely removed**. All financial relief flows through audited **Discretionary Account Balance Adjustments**.

## What changed

Early drafts included a Scholarships module with dedicated tables and workflow. The final revision purges it.

## Why it changed

- Scholarships and discretionary discounts served the same purpose: lowering a student's bill.
- Two parallel systems created accounting ambiguity and audit gaps.
- A single audited adjustment flow with reason codes is cleaner and more accountable.

## What this means in practice

- Admins apply discounts via the **Discretionary Account Adjustments** screen on a student's billing record.
- Every adjustment requires a **reason code** and an **administrative note**.
- Every adjustment is fully audited under the performing admin's identity.

## Common mistake

> [!caution] Do not
> Re-create scholarship tables or scholarship UI screens. If a stakeholder asks for "scholarships", route them to the Discretionary Adjustments workflow.

# Fee Templates vs Dynamic Service Enrollment

> [!success] Surviving rule
> The Fee Templates module is **completely removed**. Pricing is configured dynamically via service enrollment logic.

## What changed

Early drafts included a Fee Templates module for pre-defined billing templates. The final revision removes it.

## Why it changed

- Fee templates encouraged stale pricing that drifted from reality.
- Dynamic service enrollment lets admins attach costs directly to specific services per student.
- Removes a layer of indirection between enrollment and billing.

## What this means in practice

- Each service (Tuition, Transport, Clubs, Therapy) has its own pricing configuration.
- Pricing attaches to enrollment, not to a separate template entity.
- Adjustments happen at the student account level via Discretionary Adjustments.

## Common mistake

> [!caution] Do not
> Build UI for managing "fee templates". Build UI for managing **services** and their pricing rules.

# Client Mobile App vs Web Portal Only

> [!success] Surviving rule
> Parents and Students access the platform **exclusively through Web Portal browsers**. There is no native mobile app for clients.

## What changed

Some mid-tier drafts implied a client mobile app. The final revision rules it out completely.

## Why it changed

- Maintaining a native client app doubles the surface area for security review.
- A responsive web portal covers all client use cases (view grades, submit absences, see dues).
- Parents only need read-only access; a browser is sufficient.

## What this means in practice

- The Android app in the app store is **staff-only**.
- The web portal must be fully responsive on phone browsers.
- Parent auth is Google OAuth + 6-7 digit family link code, not native app SSO.

## Common mistake

> [!caution] Do not
> Advertise or design a "Parent App". All client marketing should reference the web portal URL.

# Mobile Partial Parity vs Full Parity

> [!success] Surviving rule
> The Staff Android Mobile App provides **100% data read and operational parity** with the Desktop Terminal, except for a small set of physically impossible operations.

## What changed

Earlier drafts suggested the mobile app was a "streamlined" subset. The final revision mandates full parity.

## Why it changed

- Staff frequently switch between desktop and mobile during the day.
- Inconsistent data views create confusion and operational errors.
- Modern Android hardware can render any data the desktop can.

## What this means in practice

- Every profile, ledger, debt metric, and student record visible on Desktop **must** be visible on Mobile.
- Multi-column desktop tables adapt into vertical card feeds on Mobile.
- Three operations remain desktop-only because of hardware constraints:
  - Local database backup generation
  - Raw `.xlsx` file parsing
  - Visual DAG node canvas editing

## Common mistake

> [!caution] Do not
> Hide fields or tabs from the mobile app "to save space". Convert them to a different layout, but never omit them.

# Backup Inside vs Outside Supabase

> [!success] Surviving rule
> System backups **must never reside inside the primary Supabase instance**. The Desktop terminal drives a 24-hour AES-256 encrypted archive to a local or offsite vault.

## What changed

Early drafts mentioned Supabase as both the primary database and a possible backup target. The final revision strictly isolates them.

## Why it changed

- Supabase free tier has storage limits; backups could push the database over quota.
- A Supabase outage would take down both primary data and backups if co-located.
- Local/offsite encrypted vaults survive complete cloud failures.

## What this means in practice

- The Desktop terminal runs a daily cron that pulls a full PostgreSQL dump plus media bucket assets.
- The dump is compressed, AES-256 encrypted, and written to `backup-YYYY-MM-DD-HHMMSS.db`.
- A rolling 365-day retention window supports point-in-time restoration.
- The Mobile app is **strictly prohibited** from generating or storing any backup file.

## Common mistake

> [!caution] Do not
> Configure Supabase Storage as a backup destination. Use it only for live media assets (receipts, check scans, justification documents).

# Platform Topology

> [!abstract] What it is
> The El-Imtiyaz platform is a three-frontend system anchored by a single Supabase backend. Each frontend serves a specific audience.

## The four pieces

```mermaid
flowchart TD
    SUPA["Supabase Backend Hub<br/>PostgreSQL + Auth + Edge Functions"]
    DESK["Desktop Terminal<br/>Full administrative control"]
    MOB["Staff Android App<br/>Touch-optimized operations"]
    WEB["Client Web Portal<br/>Browser-only for parents & students"]

    DESK -- REST / JWT --> SUPA
    MOB -- REST / JWT --> SUPA
    WEB -- OAuth + Link Code --> SUPA
```

## Why this shape

- **One backend** keeps a single source of truth and simplifies audits.
- **Three frontends** match three distinct usage patterns (desk work, field work, client self-service).
- **No client mobile app** eliminates a whole category of distribution and security overhead.

## Important parts to remember

- All three frontends authenticate via Supabase Auth and JWT.
- The Desktop terminal is the **only** node that runs backup routines.
- The Mobile app is the **only** node with native camera receipt capture.
- The Web Portal is the **only** node parents and students can use.

## Common mistake

> [!caution] Do not
> Build features into a frontend that the audience cannot reach. Example: do not put "Approve Expense" buttons in the Client Web Portal.

# Account Activation Protocol

> [!abstract] What it is
> The 4-step flow that activates a Parent Web Portal account and binds it to a master Parent profile.

# Parent-First Entity Dependency

> [!abstract] What it is
> A Student record cannot exist in the database without an associated Parent profile. The schema enforces this via a mandatory foreign key.

## Why it matters

This rule prevents orphaned student records, ensures every student has a billing contact, and keeps the relational graph clean for family-level reporting.

## Important parts

- The `students` table has a NOT NULL `parent_id` foreign key.
- The relationship can be modeled as either:
  - A direct `parent_id` column, **or**
  - A junction table `parent_student_links` (supports multiple guardians per student).
- Deleting or archiving a Parent requires either cascade or reassignment of dependent Students.

## Common mistake

> [!caution] Do not
> Allow a "create student" form that does not first select or create a Parent. The UI must enforce the dependency visually before submission.

> A Parent/Guardian profile can be linked to an **unlimited number ($N$) of dependent children**. The earlier 4-child cap is removed.

## Why it matters

Real families vary in size. The cap produced awkward edge cases (5th child required a second parent record) and forced artificial data sharding. The unlimited model keeps each family in a single, queryable unit.

## How it scales

```mermaid
flowchart TD
    P["Parent Profile"]
    S1["Student 1"]
    S2["Student 2"]
    S3["Student 3"]
    SN["Student N (no upper bound)"]
    P --> S1
    P --> S2
    P --> S3
    P --> SN
```

## Implementation notes

- Use a `parent_student_links` junction table or a `parent_ids_json` array column.
- The batch registration form exposes an **"Add Another Child"** button with no upper bound.
- The atomic transaction wraps Parent + all $N$ Students in a single `BEGIN...COMMIT`.

## Common mistake

> [!caution] Do not
> Hard-code an array of 4 student slots in the UI. Always render the children list dynamically from the database.

# Dynamic Batch Registration Workflow

> [!abstract] What it is
> A single-form workflow that creates a Parent profile and $1 \dots N$ linked Student records in one atomic database transaction.

## Why it matters

Without batch registration, staff had to create a parent, save, then create each child separately. That flow produced partial records when network or validation failed mid-way. The atomic batch guarantees all-or-nothing integrity.

## The 4-step flow

```mermaid
flowchart TD
    S1["Step 1: Parent Master Info<br/>Name, Phone, Email, National ID, Address"]
    S2["Step 2: Dynamic Children Blocks<br/>Add 1 to N child records"]
    S3["Step 3: Configure Billing & Discounts<br/>Per-child services and installments"]
    S4["Step 4: Atomic DB Write<br/>BEGIN ... COMMIT"]
    S1 --> S2 --> S3 --> S4
```

## Form fields

**Parent block**
- First Name, Last Name, Primary Phone, Secondary Phone
- Email, National Identity Number, Physical Address, Occupation
- Relationship (`Father`, `Mother`, `Guardian`)

**Each child block (repeatable $1 \dots N$)**
- First Name, Middle Name, Last Name
- Date of Birth, Gender
- Assigned Academic Level & Class (*Scolarite* grade)
- Enrolled Special Programs & Extracurricular Clubs
- Specific Service Enrollments (Transport, Canteen, Psychotherapy, Speech Therapy)
- Applied Discretionary Account Adjustments / Balance Discounts

## Atomic execution

The submission runs inside a database transaction (`BEGIN...COMMIT`). If creation fails for the $N$-th child, the entire operation (including the Parent record) rolls back. No orphaned data, no partial families.

## Common mistake

> [!caution] Do not
> Commit the Parent record before validating all child blocks. Validate the entire form first, then commit once.

# Subject Coefficients

> [!abstract] What it is
> Each subject carries a customizable **coefficient** (weight) used in the overall GPA calculation. Higher-coefficient subjects have more impact on the final grade.

## Why it matters

Coefficients reflect institutional priorities. Mathematics might carry a coefficient of 4 while Arts carries 1, making math performance more consequential to a student's promotion outcome.

## How coefficients work

The GPA formula multiplies each subject average by its coefficient, sums those products, and divides by the sum of all coefficients:

$$\text{Overall GPA} = \frac{\sum (\text{Subject Average} \times \text{Subject Coefficient})}{\sum \text{Subject Coefficients}}$$

See [[03. Overall GPA Calculation]] for the full breakdown.

## Administrator controls

- Administrators hold the rights to create teacher profiles and configure subjects.
- Each subject supports customizable weightings/coefficients for final score calculations.
- Coefficient changes are audited (see [[12. Security and Audit]]).

## Common mistake

> [!caution] Do not
> Change a coefficient mid-term without re-running GPAs. Coefficient edits should trigger an automatic GPA recompute for affected students.

# Assessment Structure

> [!abstract] What it is
> Every subject evaluation uses three standardized assessment inputs, each scored out of 20.

## The three inputs

| Input | French | Weight |
| :--- | :--- | :--- |
| Test 1 | *Devoir 1* | 1x |

Two tests plus a final exam gives teachers enough signal to evaluate steady progress (tests) and end-of-term mastery (exam). Doubling the exam weight ensures it dominates the average without overwhelming the tests.

# Subject Average Formula

> [!abstract] What it is
> The formula that converts the three assessment inputs into a single per-subject average.

## The formula

$$\text{Subject Average} = \frac{\text{Devoir 1} + \text{Devoir 2} + (\text{Examen} \times 2)}{4}$$

## Why this formula

- Tests 1 and 2 each contribute 1 unit of weight.
- The Final Exam contributes 2 units of weight (it covers the whole term).
- The denominator is 4 (= 1 + 1 + 2), so the average is correctly scaled back to a 0-20 range.

## Worked example

| Input | Score |
| :--- | :--- |
| Devoir 1 | 14 |
| Devoir 2 | 16 |
| Examen | 18 |

$$\text{Subject Average} = \frac{14 + 16 + (18 \times 2)}{4} = \frac{66}{4} = 16.5$$

## Common mistake

> [!caution] Do not
> Forget to multiply the Examen by 2 in both the numerator and denominator. A common bug is dividing by 3 instead of 4, which inflates the average.

# Overall GPA Calculation

> [!abstract] What it is
> The formula that aggregates per-subject averages into a single cumulative yearly GPA using subject coefficients.

## The formula

$$\text{Overall GPA} = \frac{\sum (\text{Subject Average} \times \text{Subject Coefficient})}{\sum \text{Subject Coefficients}}$$

## Why this formula

Each subject contributes to the GPA proportionally to its coefficient. A coefficient-4 subject moves the GPA four times as much as a coefficient-1 subject.

## Worked example

| Subject | Average | Coefficient | Avg × Coef |
| :--- | :---: | :---: | :---: |
| Mathematics | 16.5 | 4 | 66.0 |
| Arabic | 14.0 | 3 | 42.0 |
| Physics | 12.5 | 2 | 25.0 |
| Arts | 18.0 | 1 | 18.0 |
| **Totals** | | **10** | **151.0** |

$$\text{Overall GPA} = \frac{151.0}{10} = 15.1$$

## Passing threshold

Administrators configure the minimum passing GPA (e.g., $10.00 / 20.00$). Students at or above this threshold are eligible for promotion; below means retention.

## Common mistake

> [!caution] Do not
> Compute GPA as a simple mean of subject averages. That ignores coefficients and misrepresents student performance.

# One-Click Batch Promotion Engine

> [!abstract] What it is
> A year-end automation that evaluates every student's GPA, flags them as approved or retained, and lets admins advance all approved students with a single click.

## Why it matters

Manual year-end progression is error-prone and slow. The batch engine compresses days of administrative work into a reviewed, audited, one-click operation.

## The 4-step flow

```mermaid
flowchart TD
    S1["Step 1: Calculate Yearly GPAs<br/>for all enrolled students"]
    S2["Step 2: System Auto-Flags<br/>GPA >= 10 -> APPROVED_FOR_PROMOTION<br/>GPA < 10 -> RETAINED_SAME_YEAR"]
    S3["Step 3: Admin Reviews Queue<br/>Applies manual exception overrides"]
    S4["Step 4: Execute Batch Promotion<br/>Advances approved students, archives records,<br/>re-enrolls retained students"]
    S1 --> S2 --> S3 --> S4
```

## What happens on execution

- Advances all approved students to their next sequential grade level (e.g., Primary Grade 4 → Primary Grade 5).
- Automatically updates class rosters for the upcoming academic year.
- Archives previous year academic records to the student's permanent historical profile.
- Flags retaining students to remain enrolled in their current grade year for the new academic calendar.

## Common mistake

> [!caution] Do not
> Run batch promotion without first reviewing the queue. Always allow admin overrides for edge cases (medical exceptions, family relocations, etc.).

# Payment Status Lifecycle

> [!abstract] What it is
> Every payment flows through one of three statuses. The lifecycle is enforced by the system, not by manual updates.

## Why it matters

A clear status lifecycle prevents accounting ambiguity. Staff always know whether a payment is verified, outstanding, or in clearance.

## The three statuses

```mermaid
stateDiagram-v2
    [*] --> UNPAID: Invoice issued
    UNPAID --> PENDING: Payment submitted (check/transfer)
    UNPAID --> PAID: Cash collected
    PENDING --> PAID: Bank verifies clearance
    PENDING --> UNPAID: Check bounces / transfer fails
```

| :--- | :--- |

| `PENDING` | Payment submitted (e.g., check deposited) awaiting bank verification. |

## Common mistake

> [!caution] Do not
> Manually edit a status without logging a reason. Every status transition must be audit-logged with the actor and timestamp.

# Two-Tier Approval Lifecycle

> [!abstract] What it is
> Every organizational expenditure must follow a strict 3-step lifecycle with mandatory proof-of-purchase settlement.

## Why it matters

Two-tier approval prevents unauthorized outflows and creates an audit trail for every dime. The mandatory receipt upload closes the loop, ensuring approved funds were actually spent as claimed.

## Status lifecycle

```mermaid
stateDiagram-v2
    [*] --> PENDING_APPROVAL: Staff submits request
    PENDING_APPROVAL --> APPROVED_FUNDS_RELEASED: Manager approves
    PENDING_APPROVAL --> [*]: Manager rejects
    APPROVED_FUNDS_RELEASED --> SETTLED_AND_CLOSED: Receipt uploaded & verified
```

| Step | Status After | Actor |

| 2. Authorization & Disbursement | `APPROVED_FUNDS_RELEASED` | Admin / Financial Officer |
| 3. Proof-of-Purchase Settlement | `SETTLED_AND_CLOSED` | Staff Member + Financial Officer verify |

## Common mistake

> [!caution] Do not
> Allow a ticket to skip straight from `APPROVED_FUNDS_RELEASED` to closed. The receipt upload step is mandatory.

# Authorization and Disbursement

> [!abstract] What it is
> Tier 2 of the expense workflow. A financial officer or admin reviews the pending ticket and either approves (releasing funds) or rejects.

## Why it matters

This is the financial control gate. Without it, any staff member could spend institutional funds unilaterally.

## Approver actions

1. Review the request details and justification.
2. Inspect any attached context (photos, vendor quotes).
3. Execute `APPROVE` or `REJECT`.

## On approval

- Status changes to `APPROVED_FUNDS_RELEASED`.
- Requested capital is authorized for disbursement.
- Cash is disbursed or transfer is initiated.
- Audit log records the approver's identity and timestamp.

## On rejection

- Status returns to closed.
- Requester is notified with the rejection reason.
- No funds are released.

## Common mistake

> [!caution] Do not
> Allow self-approval. The approver must be a different user from the requester.

# Proof of Purchase Settlement

> [!abstract] What it is
> Tier 3 of the expense workflow. After completing the field purchase, the requesting staff member uploads photographic proof of the receipt to close the ticket.

## Why it matters

Without this step, there is no verification that approved funds were actually spent as claimed. The receipt upload closes the audit loop.

## Settlement steps

1. Staff completes the field transaction.
2. Staff opens the active expense ticket.
3. Staff uses the Android Mobile App camera to photograph the physical vendor receipt.
4. Staff inputs the actual final spent amount.
5. Image is uploaded (auto-compressed, sent directly to private cloud storage).
6. Financial officer verifies the receipt against the disbursed amount.
7. Ticket status updates to `SETTLED_AND_CLOSED`.

## Common mistake

> [!caution] Do not
> Let staff upload receipts from their phone's public photo gallery. The camera capture should write directly to the private bucket without leaving a public copy.

# Expense Anomaly Detection

> [!abstract] What it is
> An AI-powered safeguard that scans Tier-1 expense requests and vendor receipt descriptions to flag potential duplicates, missing documentation, or budgetary overruns.

## Why it matters

Manual review of every expense ticket is slow and error-prone. AI anomaly detection gives financial officers a prioritized queue of suspicious items to review first.

## What it flags

- **Duplicate requests:** Same vendor + same amount from different staff within a short window.
- **Missing documentation:** Tickets without attached receipts or with low-quality images.
- **Budget overruns:** Requests that exceed typical spend for the category.
- **Vendor anomalies:** Unknown vendors or vendors with no prior history.

## How it works

> [!info] Powered by AI
> This feature uses the [[02. Groq LPU API]] and [[03. OpenRouter Gateway]] under the hood. See [[11. AI Integration]].

## Common mistake

> [!caution] Do not
> Auto-reject tickets based on anomaly flags. The flag is a signal, not a verdict. A human financial officer must always make the final call.

> [!abstract] What it is
> The serverless runtime that executes workflow automations 24/7, built on Deno/TypeScript.

# Trigger Types

> [!abstract] What it is
> Triggers are the entry points of a workflow. The platform supports two categories: automated event triggers and manual action triggers.

## Why it matters

Choosing the right trigger type determines when (and whether) a workflow runs. Time-based triggers fire on a schedule; state-based triggers fire on database events; manual triggers fire on admin demand.

## Automated event triggers

| Sub-type | Example |
| :--- | :--- |
| Time-based (cron) | "Check for upcoming installment due dates every morning at 08:00 AM." |
| State-based (DB event) | "Student GPA calculated below passing threshold." |
| State-based (DB event) | "Payment record updated to `UNPAID`." |

## Manual action triggers (one-click)

Single-button administrative triggers executed on-demand:

- "Broadcast Overdue Payment Reminders"
- "Execute Batch Year-End Promotion"

## Common mistake

> [!caution] Do not
> Use a manual trigger for time-sensitive automations. If something must run every morning, use a cron trigger so it does not depend on a human remembering.

# Condition Evaluator

> [!abstract] What it is
> The engine inside each workflow that evaluates complex Boolean logic trees to decide whether actions should fire.

## Why it matters

Real-world automation rules are rarely "if X then Y". They usually look like "if debt > 10,000 DZD AND days overdue > 15 AND no payment in last 30 days, then send urgent reminder and lock portal access". The condition evaluator handles that complexity.

## Supported logic

| Operator | Use |
| :--- | :--- |
| `AND` | All conditions must be true. |
| `OR` | Any condition can be true. |
| `NOT` | Inverts a condition. |
| `>`, `<`, `>=`, `<=`, `==`, `!=` | Numerical and status comparisons. |

## Worked example

> **Rule:** If `student.absence_count >= 3` AND `student.has_medical_certificate == false`, THEN send parent alert.

## Common mistake

> [!caution] Do not
> Build conditions that reference fields not exposed in the workflow context. Always validate field availability before evaluating.

# OpenRouter Gateway

> [!abstract] What it is
> OpenRouter is a multi-model API gateway that routes requests to diverse LLMs (Anthropic, OpenAI, Mistral, etc.). It serves as a fallback when Groq is rate-limited or when a different model is better suited to a task.

## Why it matters

No single LLM provider is perfect for every prompt. OpenRouter lets the platform try multiple models without re-implementing integrations for each one.

## When it is used

- Fallback when Groq returns 429 (rate limit exceeded).
- Specific use cases where a different model outperforms Groq (e.g., long-context tasks).
- BYOK configurations where an institution has OpenRouter credits but not Groq credits.

## Common mistake

> [!caution] Do not
> Send the same prompt to both Groq and OpenRouter in parallel "to be safe". That doubles the cost and rate-limit pressure. Use OpenRouter only as a fallback.

# Bring Your Own Key (BYOK)

> [!abstract] What it is
> Institutions can input their own proprietary Groq or OpenRouter API keys in the **Settings** panel to unlock unlimited higher-tier model processing.

## Why it matters

The default rate-limited keys are fine for evaluation but will throttle under real load. BYOK lets institutions pay for their own usage and avoid shared-rate-limit bottlenecks.

## How it works

1. Admin navigates to Settings → AI Configuration.
2. Admin pastes a Groq API key and/or an OpenRouter API key.
3. System stores the keys encrypted in Supabase secrets.
4. All subsequent AI calls use the institution's keys instead of the default keys.

## Common mistake

> [!caution] Do not
> Store BYOK keys in plaintext in the database. Use Supabase secrets (server-side only) and never expose them to the browser or mobile client.

# Universal Action Traceability

> [!abstract] What it is
> The application enforces absolute user traceability. Every user operates via a unique, non-shareable user account. Anonymous or untracked state changes are strictly prohibited.

## Why it matters

Without universal traceability, audit defense becomes impossible. "Who changed this grade?" must always have a defensible answer.

## Scope of tracked events

The logging subsystem captures:

- Every database write operation (Create, Update, Delete).
- Authentication events (login, logout, failed attempts).
- Permission alterations.
- System exports (PDF, XLSX).
- Data access requests (sensitive record views).

## Critical rule

> [!danger] No anonymous operations
> Anonymous operations are strictly impossible. Even system-initiated actions (e.g., a workflow running) are attributed to a system user ID, not to "anonymous".

## Common mistake

> [!caution] Do not
> Build any "quick fix" path that bypasses the audit layer (e.g., direct SQL updates via admin shell). Every state change must flow through the audited service layer.

# Contextual Audit Schema

> [!abstract] What it is
> The full field list captured by every audit log entry. Each entry is an append-only record.

## Why it matters

A log with just "user X did something at time T" is nearly useless for investigation. The contextual schema captures enough metadata to reconstruct what happened, who did it, and from where.

## The schema

| Field | Example |
| :--- | :--- |
| `timestamp` | `2026-07-25 14:32:11.482` (UTC, high-precision) |
| `actor_id` | `UUID: 7f9e2a1c-...` |
| `actor_name` | "Amina Bouzid" |
| `role` | "Financial Officer" |
| `action` | `payment.recorded` |
| `entity_type` | `payment` |
| `entity_id` | `RCP-2026-00042` |
| `before_json` | `{"status": "UNPAID", ...}` |
| `after_json` | `{"status": "PAID", ...}` |
| `session_telemetry` | `{ip, device, session_id}` |

## Common mistake

> [!caution] Do not
> Truncate or omit `before_json` / `after_json` to save storage. Complete JSON deltas are the whole point of the audit log.

# Password Governance

> [!abstract] What it is
> Strict security controls around credential changes. Every password alteration triggers a high-priority audit event and revokes active sessions.

## Why it matters

Password changes are a common attack vector (account takeover, insider threat). Logging every change and invalidating sessions limits the damage window.

## What triggers a security event

| Event | Audit Priority |
| :--- | :--- |
| Self-service password reset | High |
| Administrator force-reset | High |
| Credential update (user-initiated) | High |

## Captured metadata

- Requester ID (who asked for the change).
- Executor ID (who performed the change; may differ from requester for admin force-resets).
- Timestamp of execution.

## Session invalidation

> [!warning] Automatic session revocation
> Modifying a password automatically revokes all active JWT tokens and terminates active sessions across all devices for that user account.

## Common mistake

> [!caution] Do not
> Allow password changes without re-authentication. The user must prove current credentials before setting a new password.

# Multi-Tenant Data Isolation

> [!abstract] What it is
> System-wide Row-Level Security (RLS) policies and explicit tenant isolation mechanisms enforced at the database level.

## Why it matters

If the platform ever expands to serve multiple institutions from one Supabase instance, RLS prevents cross-tenant data leaks. Even within a single institution, RLS prevents a parent from viewing another family's data.

## How it works

- Every table has a `tenant_id` column (or equivalent).
- Supabase RLS policies filter rows based on the JWT claim of the requesting user.
- Users are strictly prohibited from viewing, modifying, or querying data belonging to other accounts or unauthorized organizational units.

## Common mistake

> [!caution] Do not
> Bypass RLS by using the `service_role` key in client code. The service_role key skips RLS and should only be used server-side in Edge Functions.

# Media Asset Vaulting

> [!abstract] What it is
> Documents containing sensitive personal identity details or financial transaction proofs are stored in private, signed-URL storage buckets.

## Why it matters

Receipt photos, check scans, and medical certificates are sensitive. Public URLs would expose them to anyone with the link, including search engine crawlers.

## The rule

> [!danger] No public URLs
> Direct public URL access to media assets is strictly forbidden. Access requires temporary signed tokens validated against active user permissions.

## How signed URLs work

1. Client requests access to a media asset.
2. Server validates the user's permission to view that asset.
3. Server generates a time-limited signed URL (e.g., 5-minute expiry).
4. Client downloads the asset via the signed URL.
5. URL expires; subsequent requests require a new signed URL.

## Common mistake

> [!caution] Do not
> Cache signed URLs in client-side storage for reuse. Always request a fresh signed URL when displaying media.

# 24-Hour Backup Cycle

> [!abstract] What it is
> An automated daemon running on the Desktop Master Terminal executes a full system backup every **24 hours**.

## Why it matters

Data loss is the single biggest threat to any institution. A daily backup cadence limits maximum data loss to 24 hours of operations, which is acceptable for a school's transaction volume.

## What the backup captures

1. Complete PostgreSQL database dump (schema, tables, views, procedures).
2. System configuration state and workflow schemas.
3. All secure media bucket assets (scanned checks, payment proof images, vendor receipts, uploaded documents).

## Critical isolation rule

> [!danger] Backups never live in Supabase
> To protect against Supabase platform downtime or free-tier constraints, **backups must never reside inside the primary Supabase instance**. They are pulled out to a Desktop-driven local/offsite vault.

## Common mistake

> [!caution] Do not
> Run the backup during peak operating hours. Schedule it for 02:00 AM local time to minimize user impact.

# AES-256 Encryption

> [!abstract] What it is
> All backup archives are compressed and encrypted at rest using **AES-256** standards prior to physical disk write.

## Why it matters

A stolen backup file without encryption is a catastrophic data breach. AES-256 is the industry standard for encrypting data at rest and is considered computationally infeasible to brute-force.

## How it works

1. Desktop terminal extracts the PostgreSQL dump and media assets.
2. Compresses the payload (gzip or zstd).
3. Encrypts the compressed archive with AES-256 using a key stored in a separate secrets manager.
4. Writes the encrypted archive (`backup-YYYY-MM-DD-HHMMSS.db`) to local/offsite vault.

## Key management

> [!warning] Protect the encryption key
> The AES-256 key must be stored separately from the backup files. If the key and the backups are stored together, encryption provides no protection.

## Common mistake

> [!caution] Do not
> Hard-code the AES key in the backup script. Use a secrets manager or hardware security module (HSM).

# Offsite Vault Storage

> [!abstract] What it is
> Backups are archived to a designated local server or secondary encrypted offsite storage vault.

## Why it matters

If the Desktop terminal is destroyed (theft, fire, hardware failure), locally-stored backups die with it. An offsite vault ensures business continuity.

## Recommended topology

```mermaid
flowchart TD
    DT["Desktop Terminal<br/>(runs backup)"]
    LOCAL["Local External Drive<br/>(fast restore)"]
    OFFSITE["Offsite Vault<br/>(disaster recovery)"]
    DT --> LOCAL
    DT --> OFFSITE
```

## Retention

- Rolling **365-day** retention window.
- Daily snapshots, so up to 365 distinct restore points.
- Older backups are automatically purged after 365 days.

## Common mistake

> [!caution] Do not
> Use the same physical location for both local and offsite backups. A single fire or flood would destroy both copies.

# Point-in-Time Restoration

> [!abstract] What it is
> Backup archives maintain version control metadata allowing complete system rollbacks to any 24-hour snapshot over a rolling 365-day retention window.

## Why it matters

A data corruption event discovered three days later requires rolling back to a state from before the corruption. Point-in-time restoration makes that possible.

## How to restore

1. Admin opens the Desktop terminal's restoration interface.
2. Selects a backup archive by date (`backup-2026-07-22-020000.db`).
3. System decrypts and decompresses the archive.
4. System halts write operations on the primary database.
5. System restores the dump to Supabase.
6. System restores media assets to the Storage bucket.
7. Admin verifies integrity and resumes operations.

## Common mistake

> [!caution] Do not
> Restore into the production database without first testing the restore in a staging environment. A corrupt restore can compound the original data loss.

# Mobile Backup Prohibition

> [!abstract] What it is
> The Staff Android Mobile App is **strictly prohibited** from generating, downloading, or storing local database archives or backup archives.

## Why it matters

Mobile devices are physically insecure: they get lost, stolen, or resold. A backup file on a phone is a data breach waiting to happen.

## The rule

> [!danger] Zero local mobile backups
> The Android app is explicitly prohibited from running backup operations or storing backup dumps on phone storage.

## Why this matters operationally

- Phone storage is limited; backups would crowd out photos and apps.
- Mobile local file systems are more vulnerable to side-channel attacks.
- Lost devices would expose institutional data.

## Architecture implication

All mobile operations interact directly with Supabase via authenticated REST/gRPC API calls. Camera images stream directly to private cloud storage buckets without remaining in the mobile device's public media gallery.

## Common mistake

> [!caution] Do not
> Add a "Download Backup" button to the mobile app "for convenience". This is a critical security violation.

# Excel Engine Deprecation

> [!abstract] What it is
> All in-app spreadsheet evaluation logic — formula parser, cell-matching engine, Devis quote sheet reproduction, and column-AM comment text parsers — is **completely removed** from the system.

## Why it matters

The embedded Excel engine was a parallel logic system that duplicated what the relational database already did. Maintaining it created audit gaps, security risks, and a maintenance burden.

## What was removed

| Removed Module | What it did |
| :--- | :--- |
| Formula Parser | Evaluated `SUM`, `VLOOKUP`, `INDEX`, `MATCH`, `IF`, etc. |
| Cell-Matching Engine | Matched spreadsheet cells to database entities. |
| Devis Quote Sheet Reproduction | Replicated the original school workbook's quote layout. |
| Column-AM Comment Parsers | Parsed free-text comments in spreadsheet column AM into structured data. |
| Spreadsheet Template Mapping | Mapped spreadsheet layouts to database schemas. |

## What survives

Excel survives **only** as a two-way data bridge:

1. **Import Students:** Parsing `.xlsx` roster files to bulk-register students and parents on Desktop.
2. **Export Data:** Generating `.xlsx` or `.csv` files for financial and administrative reports on Desktop.

## Common mistake

> [!caution] Do not
> Re-introduce `ExcelJS` formula parsing into runtime code paths. The library may remain imported, but only inside the import and export service modules.

# Student Bulk Import Pipeline

> [!abstract] What it is
> The Desktop-only pipeline that reads `.xlsx` roster files and bulk-creates Parent and Student records.

## Why it matters

At the start of an academic year, hundreds of students need to be enrolled. Manual entry would take days; bulk import compresses it to minutes.

## The 5-step pipeline

```mermaid
flowchart TD
    S1["Step 1: Staff selects .xlsx file<br/>via OS file picker"]
    S2["Step 2: ExcelJS parses binary workbook"]
    S3["Step 3: Maps spreadsheet headers<br/>to database fields"]
    S4["Step 4: Validates required fields,<br/>missing parent links, invalid grade codes"]
    S5["Step 5: Atomic bulk insert<br/>into parents + students tables"]
    S1 --> S2 --> S3 --> S4 --> S5
```

## Field mapping

Spreadsheet column headers are mapped to database attributes:

| Spreadsheet Column | Database Field |
| :--- | :--- |
| Student Name | `students.full_name` |
| Parent Contact | `parents.primary_phone` |
| DOB | `students.date_of_birth` |
| Class Level | `students.grade_level_id` |

## Validation

- Required fields must be present.
- Duplicate student codes are rejected.
- Parent links must be valid (no orphaned students).
- Grade codes must match the configured Scolarite hierarchy.

## Common mistake

> [!caution] Do not
> Allow partial imports. If any row fails validation, the entire import should roll back via atomic transaction.

# Atomic Database Transactions

> [!abstract] What it is
> Multi-record writes (e.g., batch student creation, bulk imports) must be wrapped in a database transaction (`BEGIN...COMMIT`). If any record fails, the entire operation rolls back.

## Why it matters

Without atomic transactions, a partial failure creates orphaned data (e.g., a Parent record with only 2 of 5 children created). Orphans break referential integrity and confuse reporting.

## Pattern

```sql
BEGIN;
  INSERT INTO parents (...) VALUES (...);
  -- parent_id is now available
  INSERT INTO students (parent_id, ...) VALUES (parent_id, ...);
  INSERT INTO students (parent_id, ...) VALUES (parent_id, ...);
  -- if any INSERT fails, ROLLBACK fires automatically
COMMIT;
```

## When to use

- Batch student creation (1 parent + N students).
- Bulk Excel imports.
- Two-tier expense workflow transitions.
- One-click batch promotion (advancing N students).

## Common mistake

> [!caution] Do not
> Commit the Parent record before validating all child records. Validate first, commit once.

# Audit Trail Hygiene

> [!abstract] What it is
> Habits that keep the audit trail useful for investigations and compliance defense.

## Why it matters

An audit log is only as valuable as its data quality. Sloppy logging (truncated payloads, missing actor IDs, skipped events) makes investigations impossible.

## Hygiene checklist

- [ ] Every state-changing operation writes to the audit log.
- [ ] Every audit entry includes `before_json` and `after_json` snapshots.
- [ ] Every audit entry attributes to a real user ID (or `system` for automation).
- [ ] Audit entries are append-only (no edits, no deletes).
- [ ] Sensitive fields in payloads are masked if regulatory rules require it.
- [ ] Audit log retention matches or exceeds legal requirements.

## Common mistake

> [!caution] Do not
> Truncate `before_json` / `after_json` to save storage. Storage is cheap; audit gaps are expensive.

# Parent-First Data Modeling

> [!abstract] What it is
> Always model Parent records before Student records. A Student cannot exist without a linked Parent.

## Why it matters

Orphaned student records break family-level reporting, financial consolidation, and audit trails. Parent-first modeling is enforced at the schema level.

1. Create or look up the Parent profile.
2. Validate the Parent profile (contact info, address).
3. Create the Student record with `parent_id` foreign key.
4. Attach services, enrollments, and discounts to the Student record.
5. Commit the atomic transaction.

## Common mistake

> [!caution] Do not
> Allow a "create student" form that does not first select or create a Parent. The UI must enforce the dependency visually before submission.

# Color Token Discipline

> [!abstract] What it is
> Always reference design token variables (e.g., `--color-primary-blue`) in code; never hard-code hex strings (e.g., `#349BD4`).

Hard-coded hex values scatter the color system across thousands of components. A rebrand or dark-mode tweak becomes a massive find-and-replace exercise. Tokens centralize the change.

## Pattern

```css
/* Good */
.button-primary {
  background-color: var(--color-primary-blue);
  color: var(--color-off-white-text);
}

/* Bad */
.button-primary {
  background-color: #349BD4;
  color: #EFF2F3;
}
```

## Common mistake

> [!caution] Do not
> Copy hex strings from Figma into components. Always port them into the token file first, then reference the token.

# Orphaned Student Records

> [!abstract] Symptom
> A Student record exists with no linked Parent. The bidirectional navigation breaks; family balance reports are wrong.

## Likely causes

- A code path bypassed the `parent_id` foreign key check.
- A Parent was deleted without cascading or reassigning children.
- A bulk import skipped the parent creation step.

## Diagnostic queries

```sql
-- Find orphaned students
SELECT id, full_name, parent_id
FROM students
WHERE parent_id IS NULL
   OR parent_id NOT IN (SELECT id FROM parents);
```

## Fix

1. Identify the orphaned students.
2. Either:
   - Create a Parent record and link it, **or**
   - Reassign the student to an existing Parent (e.g., if the original Parent was deleted).
3. Audit-log the fix.

## Prevention

- Enforce `parent_id` as NOT NULL at the schema level.
- Use atomic transactions for batch creation.
- Block Parent deletion if any Students are still linked.

# Failed Backup Verification

> [!abstract] Symptom
> The 24-hour backup daemon ran but the resulting archive is corrupted, missing, or unopenable.

## Likely causes

- Disk full on the local vault.
- AES encryption key changed without re-encrypting old archives.
- Supabase connection dropped mid-dump.
- Media bucket download timed out.

## Diagnostic checklist

- [ ] Check the backup daemon's log for the timestamp and error message.
- [ ] Verify disk space on the local vault.
- [ ] Confirm the AES key in the secrets manager matches the key used historically.
- [ ] Verify Supabase connectivity from the Desktop terminal.
- [ ] Test restoring the most recent successful backup.

## Fix

1. Resolve the root cause (free disk space, restore key, fix network).
2. Trigger an ad-hoc backup to verify the fix.
3. Verify the new archive by attempting a test restore in staging.

## Prevention

- Disk space alerting at 80% capacity on the vault.
- Backup success/failure notification via Edge Function.
- Weekly test restore in staging environment.

# Sync Conflicts in Offline Mode

> [!abstract] Symptom
> The Mobile app recorded attendance (or expense requests) while offline, and the sync to Supabase fails or produces conflicting records.

## Likely causes

- Same record was modified on Desktop while Mobile was offline.
- Network reconnection happened mid-sync, leaving partial uploads.
- Local Room DB schema drifted from server schema after an update.

## Diagnostic checklist

- [ ] Check the mobile sync queue for stuck records.
- [ ] Compare local Room DB timestamps with server timestamps.
- [ ] Look for duplicate records with matching client-side IDs.

## Fix

1. Identify the conflicting records.
2. Apply last-write-wins for non-critical fields (e.g., notes).
3. Surface critical conflicts (e.g., payment amounts) to the user for manual resolution.
4. Once resolved, mark the sync queue item as completed.

## Prevention

- Always include a `client_updated_at` timestamp on mobile records.
- Use server-side `updated_at` comparison to detect stale writes.
- Surface sync failures prominently in the mobile UI.

# Workflow Not Firing

> A workflow automation was deployed but is not executing when its trigger condition is met.

## Likely causes

- Trigger node misconfigured (wrong event type, wrong field).
- Condition evaluator returns false due to a logic bug.
- Edge Function deployment failed silently.
- Workflow is in "Draft" status, not "Published".

## Diagnostic checklist

- [ ] Verify workflow status is `Published`, not `Draft`.
- [ ] Check Edge Function logs in Supabase for execution records.
- [ ] Manually trigger the workflow to confirm the action chain works.
- [ ] Inspect the condition evaluator's input data.
- [ ] Verify the trigger event is actually firing in the database.

## Fix

1. Identify the failing node (trigger, condition, or action).
2. Patch the node configuration.
3. Re-deploy to Edge Functions.
4. Test with mock data.

## Prevention

- Always test workflows with mock data before publishing.
- Add an audit log action as the final node so silent failures become visible.
- Monitor Edge Function execution logs.

# DAG Cycle Detection Errors

> [!abstract] Symptom
> The visual DAG canvas rejects a workflow with a "cycle detected" error when the user tries to publish.

## Likely causes

- A node's output connects back to an upstream node, forming a loop.
- A `Transform` node feeds back into a `Trigger` node.
- Visual layout hides a back-edge that the algorithm catches.

## Diagnostic checklist

- [ ] Trace every path from each Trigger node.
- [ ] Look for any path that returns to a node already on the current path.
- [ ] Use the canvas's "Highlight Cycles" feature if available.

## Fix

1. Identify the back-edge causing the cycle.
2. Either:
   - Remove the back-edge, **or**
   - Insert a `Delay` and `Transform` pair to break the cycle into a finite sequence.
3. Re-run Kahn's algorithm to verify acyclicity.
4. Publish the workflow.

## Prevention

- Run cycle detection on every canvas save, not just on publish.
- Provide visual feedback (red edges) when a connection would create a cycle.
